# PMD 双文档模板

> 源自《PRD 产品需求文档模板（2026/04/10）》。章节标签含义见文末"填写规则说明"。
>
> 本文件是两份最终产物的唯一权威正文结构。下面的完整 `analysis.md` 与 `prd.md` 正文模板必须全部读取、完整保留并逐项填写；`skills/pmd-prd/templates.md` 仅是导航指针，任何摘要都不能替代本文件。公司 PRD 的 fenced 正文模板不得修改、删节或追加。
>
> 阶段 5 的冻结过程文件使用 `{需求标识}_{主题}_01_需求分析与研发交付.md` 与 `{需求标识}_{主题}_02_PRD.md`。缺失必填信息写 `[待确认]` 并说明影响，选填项不适用写“不适用（原因）”；冻结后必须先通过 `scripts/validate-deliverables.mjs`，再进入 batch preview。

## analysis.md 固定模板（面向产品与研发）

```markdown
# 需求分析与研发交付：{编号} - {主题}

## 1. 需求最终理解
{已对齐的目标、使用者、范围、非目标和待确认项。}

## 2. 产品纠正
{逐轮列出：AI 原理解、产品纠正、最终理解、影响。没有纠正时写“不适用（原因）”。}

## 3. 最终业务规则
{按业务场景写已确认规则、输入/输出、例外处理和边界；未知项写 `[待确认]`。}

## 4. 代码修改位置
| 改什么 | 在哪里改 | 怎么改 | 改完效果 |
|---|---|---|---|
| | 仓库 / 文件 / 函数 / 行号（能确认时填写） | | |

## 5. 具体修改方式
{按上表逐项说明修改步骤、依赖和仍待确认事项；不编造代码事实。}

## 6. 验收清单
### 正常情况
- [ ] {至少列出一项正常使用检查。}

### 异常情况
- [ ] {至少列出一项异常处理检查。}

### 边界情况
- [ ] {至少列出一项边界检查。}

### 权限情况
- [ ] {至少列出一项权限检查；确实不涉及时写“不适用（原因）”。}

### 兼容情况
- [ ] {至少列出一项原有功能兼容检查。}
```

填写约束：第一份文档只展示已确认结论和待确认项，不展示内部过程术语、内部编号或追踪链。代码位置只能来自实际查询；无法确认时写 `[待确认]`。验收清单必须覆盖正常、异常、边界、权限和兼容五类。

# 二、背景与目标

## （一）描述/痛点 [必填]

{内容可包含当前业务痛点、本需求服务于的用户角色、影响的用户规模（内部/外部用户、覆盖范围与量级）。**必须提供客观数据依据**，如月均工单量、受影响订单数、资损金额、业务效率数据、投诉率等，并说明需求来源。纯主观判断或单一客户口头反馈不得作为需求立项的唯一依据。产品经理有责任协助业务方补充数据支撑，或主动调取系统数据进行验证。}

## （二）目标/价值 [必填]

{说明该需求的业务价值归类（增收增润、降本提效、风控合规、用户体验、能力建设），以及需求上线后的具体衡量指标。**必须给出可量化的预期目标值和度量方式**，例如：操作时长从 X 分钟降低到 Y 分钟、差错率从 A% 降低到 B%、月均工单减少 N 件。产品经理在审核时需判断收益指标是否合理、可衡量、可归因。}

## 风险控制 【选填】

{是否涉及资金、计费、结算等资损敏感领域；是否涉及监管合规、审计要求、数据隐私、舆情等约束与风险说明。}

## 填写规则说明

| 章节标签 | 含义说明 |
|---|---|
| 必填 | 所有优先级需求（P0–P3）均须填写，缺失则不予进入需求评审。 |
| 选填 | 视需求情况填写，不涉及可注明"不适用"或留空。 |
| 建议填写 | 建议填写以提升需求质量；如不填写需在评审会上口头说明理由。 |

> 强调：背景与目标（痛点/价值）必须提供**客观数据依据**与**可量化的预期目标值**，主观判断不得作为唯一立项依据。

## 双文档生成规则（只约束生成，不进入公司 PRD 正文）

- 必填项无事实时写 `[待确认]`，说明缺口、影响和需要谁确认；不得编造数字补齐模板。
- 选填项不适用时写“不适用（原因）”，不能用无依据结论代替。
- 每个功能至少包含正常场景、输入/输出、边界、异常、权限和验收标准。
- PRD 只写最终业务结论和业务术语，不写聊天过程、代码路径、文件名、函数名、内部编号或工程追踪术语；代码细节只写入第一份研发交接包。
- 产品说“全部按推荐”只确认建议方向，不会把无来源的人天、百分比、性能值、用户反馈或系统数据变成事实。
