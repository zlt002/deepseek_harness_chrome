```markdown
# 需求分析与研发交付：{编号} - {主题}

## 1. 需求理解与范围
{目标、用户、边界、非目标、领域术语/不变量和待确认项。}

## 2. 证据分类
| Evidence ID | 类型 | 事实或结论 | 来源 | 状态 |
|---|---|---|---|---|
| E-001 | 用户事实 | | | 已确认/待确认 |
| E-002 | 知识依据 | | | 已确认/待确认 |
| E-003 | AI 推断 | | | 待确认 |

## 3. 规模评估与拆分
| 信号 | 证据 | 普通/高风险 | 结论 |
|---|---|---|---|
{触发时记录用户选择：父需求+子需求 / 单需求分阶段 / 明确接受风险继续整体分析；记录覆盖关系和依赖。}

## 4. 代码影响地图
| Impact ID | 仓库 | 模块或文件 | 符号或接口 | 当前行为 | 计划改动 | Evidence ID | 不确定项 |
|---|---|---|---|---|---|---|---|

## 5. 纵向任务
| Task ID | PRD章节 | 用户可见交付 | Impact ID/修改内容 | 阻塞关系 | 测试 seam | 验证方式 | AC ID | 完成条件 |

| AC ID | 需求/PRD章节 | Task ID | Given | When | Then | 测试数据 | 验证层级 | 命令或手工步骤 | 通过标准 | 证据 |

{依赖、发布/回滚、监控、可选原型链接或“不适用（本需求无页面交互）”。}
```

填写约束：影响地图无远程证据时写 `[待确认]`，不得编造；每个 Impact 映射 Evidence；每个 Task 映射 Impact 和至少一个 AC；每个 AC 映射需求和 Task；每项 Task 必须独立可演示或验证。

```markdown
# 二、背景与目标

## （一）描述/痛点 [必填]

{内容可包含当前业务痛点、本需求服务于的用户角色、影响的用户规模（内部/外部用户、覆盖范围与量级）。**必须提供客观数据依据**，如月均工单量、受影响订单数、资损金额、业务效率数据、投诉率等，并说明需求来源。纯主观判断或单一客户口头反馈不得作为需求立项的唯一依据。产品经理有责任协助业务方补充数据支撑，或主动调取系统数据进行验证。}

## （二）目标/价值 [必填]

{说明该需求的业务价值归类（增收增润、降本提效、风控合规、用户体验、能力建设），以及需求上线后的具体衡量指标。**必须给出可量化的预期目标值和度量方式**，例如：操作时长从 X 分钟降低到 Y 分钟、差错率从 A% 降低到 B%、月均工单减少 N 件。产品经理在审核时需判断收益指标是否合理、可衡量、可归因。}

## 风险控制 【选填】

{是否涉及资金、计费、结算等资损敏感领域；是否涉及监管合规、审计要求、数据隐私、舆情等约束与风险说明。}
```

## 填写规则说明

| 章节标签 | 含义说明 |
|---|---|
| 必填 | 所有优先级需求（P0–P3）均须填写，缺失则不予进入需求评审。 |
| 选填 | 视需求情况填写，不涉及可注明"不适用"或留空。 |
| 建议填写 | 建议填写以提升需求质量；如不填写需在评审会上口头说明理由。 |

> 强调：背景与目标（痛点/价值）必须提供**客观数据依据**与**可量化的预期目标值**，主观判断不得作为唯一立项依据。

## AccrUI 需求交接附录（必须追加，不替代上文模板）

以下内容用于把 PRD 与需求形成过程绑定，不能删减原模板章节，也不能把本附录当作原模板的替代品。

### A. 需求过程与证据分类

| 类型 | 内容 | 入口 |
|---|---|---|
| 用户事实 | 用户明确说过、确认过的目标、范围、规则和验收 | `process.md` |
| 知识依据 | 来自代码库、知识中台或正式资料的事实与引用 | `knowledge-sources.md` |
| AI 推断 | 基于事实提出的建议或实现假设 | 在正文中标记 `[AI 推断]` |
| 待确认项 | 会影响范围、行为、验收、风险或交付的未知信息 | 在对应章节标记 `[待确认]` |

### B. 需求交接索引

- 需求标识：`{requirementId}`
- 过程摘要：`process.md`
- 领域模型：`domain-model.md`
- ADR 索引：`decisions/README.md`；具体 ADR 只列真正影响实现方向的决定
- 知识来源：`knowledge-sources.md`
- 原型：`prototypes/`（无原型时写“不适用（本需求无页面交互）”）
- 机器事件：`trace-events.jsonl`（仅用于诊断，不作为研发阅读入口）

### C. 研发继续工作入口

- 开发设计：从“四、功能性需求”、领域模型和 ADR 提取模块边界、数据流、状态和异常处理。
- 开发任务：按功能、异常场景和验收标准拆解，每项任务保留本 PRD 章节引用。
- 执行计划：列出依赖、验证命令、测试数据、灰度/回滚、监控和仍待确认项。
- 代码影响地图：按 `analysis.md` 的 Impact ID 回链 Evidence、仓库、模块或文件、符号或接口、当前行为、计划改动和不确定项；未知项保持 `[待确认]`。
- 纵向任务：按 `analysis.md` 的 Task ID 回链 PRD 章节、用户可见交付、Impact ID/修改内容、阻塞关系、测试 seam、验证方式、AC ID 和完成条件；每项独立可演示或验证。
- 验收合同：按 `analysis.md` 的 AC ID 回链需求/PRD 章节、Task、Given、When、Then、测试数据、验证层级、命令或手工步骤、通过标准和证据。

### D. 生成完整性规则

- 原模板章节必须按原顺序保留；不得因为当前信息不足而删除章节。
- 必填项无事实时写 `[待确认]`，说明缺口、影响和需要谁确认；禁止留空或编造。
- 选填项不适用时写“不适用（原因）”，不能用空白代替。
- 每个功能至少包含正常场景、输入/输出、边界、异常、权限和验收标准；代码库能够确认的现状应写明依据。
- PRD 只写结论和索引，不复制完整聊天记录或机器事件；过程原因回看 `process.md`，技术诊断回看 `trace-events.jsonl`。
- 每个 Impact 必须映射 Evidence；每个 Task 必须映射 Impact 和至少一个 AC；每个 AC 必须映射需求和 Task；映射不完整时不得冻结双文档。
