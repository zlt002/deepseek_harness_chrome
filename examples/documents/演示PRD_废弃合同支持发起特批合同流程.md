# 二、背景与目标

## （一）背景与痛点

原合同未归档但需继续经营时，业务可能以新的合同号重复发起同一业务，导致收入、成本与有效合同号不一致。需求拟通过“申请废弃标识”和“特批合同”建立同合同集内的可追溯关系。以上为来源文档的业务描述，现行规则待业务确认。

## （二）目标与价值

| 项目 | 内容 |
|---|---|
| 目标 | 当原合同处于申请废弃或已废弃场景时，支持从原合同发起特批合同；避免重复以新合同号重建同一业务。 |
| 涉及模块 | 合同详情、合同列表/查询、合同导出、法务回调、BMS 交易规则、通知。 |
| 本次改动 | 改造“申请废弃”“撤销废弃”；新增“特批合同”按钮、三个业务字段及列表筛选；补充合同集状态联动。 |
| 不在本次范围 | 不新增截图资产；原文未明确的审批人、角色 ID、接口报文及失败重试策略，不在本稿中推断。 |

## （三）风险控制

| 风险 | 控制要求 |
|---|---|
| 同一合同集出现两份有效合同 | 状态更新前校验合同集；回调重复或乱序时保持幂等，并记录冲突。具体实现待代码核验。 |
| 合同复制范围错误 | 使用字段映射和明确不复制清单；价格表及价格明细不得随特批合同复制。 |
| 跨系统状态不一致 | 法务、BMS、通知失败需要可定位、可重试或可补偿；现行机制待接口与代码核验。 |
| 权限或导出范围扩大 | 继承既有合同数据权限；新增字段不得绕过页面、接口及导出权限。 |

# 三、整体流程

1. 用户在合同详情发起“申请废弃”，系统创建变更记录并将申请废弃标识置为是。
2. 满足条件时，用户从原合同发起“特批合同”，系统复制规定的主档和明细，生成草稿。
3. 用户在特批合同中按既有流程维护并保存；是否调用法务保存草稿能力需接口核验。
4. 法务回调或撤销废弃审批通过后，系统依据原合同/特批合同及另一合同状态，更新合同状态和申请废弃标识。
5. 需要联动的计费模板、BMS 与通知按真实调用链执行；失败补偿规则待确认。
